How I Built This Blog on AWS for Free

August 1, 2026 · 5 min read

I've been meaning to set up a personal blog for a while. Not a Medium account, not a Substack — something I own and control. This weekend I finally did it, and it turned out simpler than I expected. Here's exactly how it's built.

The goal

A fast, cheap static blog deployed on AWS. No servers to manage, no runtime to babysit. Push a file to GitHub, the site updates itself. I already had AWS infrastructure experience from other projects, so I wanted to reuse the same tooling: AWS CDK for infra and GitHub Actions for the deploy pipeline.

The stack

  • S3 — stores the static HTML/CSS files. Private bucket, not publicly accessible.
  • CloudFront — CDN that sits in front of S3. Handles HTTPS, caching, and serves the site globally. This is the only thing the public touches.
  • Origin Access Control (OAC) — CloudFront gets a signed identity to read from S3. The bucket itself stays locked.
  • AWS CDK (TypeScript) — defines all of the above as code. No clicking around in the console.
  • GitHub Actions — push to main → deploy. That's the whole pipeline.

Running cost: near zero. S3 storage for a few HTML files is fractions of a cent. CloudFront's free tier covers 1TB of data transfer and 10 million requests per month — more than enough for a personal blog.

The CDK stack

The entire infrastructure is defined in a single TypeScript file — lib/blog-stack.ts. It creates the S3 bucket, the CloudFront distribution, and deploys the web/ folder to S3 on every CDK deploy. 

const siteBucket = new s3.Bucket(this, 'SiteBucket', {
  blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
  encryption: s3.BucketEncryption.S3_MANAGED,
  enforceSSL: true,
  removalPolicy: RemovalPolicy.DESTROY,
  autoDeleteObjects: true,
});

const distribution = new cloudfront.Distribution(this, 'Distribution', {
  defaultRootObject: 'index.html',
  defaultBehavior: {
    origin: origins.S3BucketOrigin.withOriginAccessControl(siteBucket),
    viewerProtocolPolicy: cloudfront.ViewerProtocolPolicy.REDIRECT_TO_HTTPS,
    cachePolicy: cloudfront.CachePolicy.CACHING_OPTIMIZED,
    compress: true,
  },
});

CDK also handles deploying the static files to S3 and invalidating the CloudFront cache — so changes go live immediately after a deploy, no manual steps.

The deploy pipeline

The GitHub Actions workflow is straightforward. On every push to main:

  1. Check out the repo
  2. Verify AWS credentials
  3. Run npm install to get CDK and its deps
  4. Run cdk synth to type-check and generate the CloudFormation template
  5. Run cdk deploy — this uploads any changed files to S3 and updates the CloudFront distribution if needed

AWS credentials live in GitHub's environment secrets (A_KEY and S_KEY). The workflow reads them, and CDK uses the standard AWS SDK credential chain to pick them up. No third-party actions needed for auth.

Writing posts

Right now posts are plain HTML files in web/posts/. It's low-tech but it works — I control every pixel, there's no build step, and the files load instantly. I'll probably add a lightweight Markdown-to-HTML step later if the number of posts grows, but for now this is fine.

To publish: write an HTML file, add a link to it on the homepage, push to main. Done in under a minute.

Custom domain (coming soon)

The site is currently on a CloudFront URL (*.cloudfront.net). I'm registering a free subdomain at is-a.dev — a free developer subdomain service. Once that's set up, I'll issue an ACM certificate in us-east-1 (required for CloudFront), add it to the CDK stack via context variables, and point the CNAME. The CDK stack already has this wired in, just waiting on the domain.

What I'd do differently

Nothing major. If I were building this for a team or expecting serious traffic, I'd add a staging environment and tag-based deploys (like I do in my other projects). For a personal blog, pushing to main is fine.

The whole thing — from idea to live site — took a couple of hours, most of which was the CDK boilerplate. The actual deploy pipeline ran first time without errors. AWS CDK remains my favourite way to define cloud infrastructure: it's just TypeScript, the constructs compose cleanly, and you get real type checking instead of hoping your YAML is valid.

The full source is at github.com/vipinable/twmblog if you want to clone and adapt it.
